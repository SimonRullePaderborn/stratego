# Experiment card: 2026-11-27-p0-arrival

## Before the run

* **Phase and gate it serves:** phase 0. Gate: throughput recorded and the cost model redone; the stored 8x8
  checkpoint reproduces its numbers on the cluster.
* **Hypothesis (one sentence):** one H100 sustains between 110 and 440 million voxel-iterations per second on
  the rule of design version 2 (32 state channels, 128 hidden units, 68 inputs; 131,072 multiply-adds per voxel
  and iteration), so a 900-round run at full scale costs 35 to 140 GPU-hours.
* **What would support it:** `cluster/bench_rule.py` times a stand-in with the structure of the old rule, which
  costs 241,664 multiply-adds per voxel and iteration in its row "24x24 proposed rule". Its best search-mode
  figure, multiplied by 241,664 / 131,072 = 1.84, lies inside that range. On the stand-in itself that is 60 to
  240 million.
* **What would refute it:** below 60 million on the stand-in. Then the dials of design section 11 shrink before
  phase 2, and every budget in the roadmap is redone.
* **The one thing that changes** relative to which earlier run: nothing is trained; this replaces estimates by
  measurements.
* **Verification done on the cluster's CPUs first:** `python3 test_sim.py` (the 8x8 consistency tests), from
  `nca_drones/`. The tests of the new simulator, `python3 -m wf.test_sim`, are step 1 of phase 1.
* **Steps, in order** (each one command over ssh; the exact commands and expected outputs are in
  `PROGRAMME.md` section 10):
  1. Connection, and the code on the cluster.
  2. `bash nca_drones/cluster/probe.sh`, on the login node and inside a GPU allocation. Its raw output is not
     committed.
  3. Python environment with a CUDA build of PyTorch: 2.15.0 if possible, which needs Python 3.11 or newer.
  4. `python3 nca_drones/cluster/bench_rule.py --out nca_drones/results/bench/h100.json`.
  5. `python3 test_sim.py` from `nca_drones/`.
  6. `python3 analyze.py results/v10/best_prereg.pt --prereg` from `nca_drones/`. Expected: 164 of 200 on the
     test set and 1,507 of 2,000 on the never-posed tasks, closed loop. The same for
     `results/v11_noshared/best_prereg.pt`: 135 of 200 and 1,309 of 2,000.
  7. Restart drill with the old trainer.
  8. The cost model redone with the measured throughput.
* **Commit:** the head of `claude/nca-drone-coordination-d2k5kw` at the time of the run.
* **Cluster job ids:** the Docker containers listed under "After the run"            **Estimated GPU-hours:** under 5
* **How the steps run on this cluster** (added before the run, from read-only checks of the node; raw output
  stays on the cluster, and step numbers below are those of `PROGRAMME.md` section 10):
  * The cluster is one DGX node, reached directly by ssh: 8 H100 80 GB (driver 580, CUDA 13.0), 2 x 56-core
    Xeon Platinum 8480CL (224 threads, two NUMA nodes), 2 TB memory. There is no scheduler (no Slurm, PBS or
    LSF); GPU work on this node runs in Docker containers. GPU 2 reports an error state in `nvidia-smi` and is
    not used. GPUs 0 and 3 carry the PI's runs of another project and are not touched. The working directory
    is `~/wf`, on a local RAID with 770 GB free (98% used, shared with other users).
  * Every job is a Docker container from the image the node already holds,
    `pytorch/pytorch:2.5.1-cuda12.4-cudnn9-runtime`, started detached under the PI's own user id, with `~/wf`
    mounted at the same path, a fixed set of CPU cores (`--cpuset-cpus`), the thread count set to match, and
    `nice -n 10`. A GPU job sees GPU 1 and nothing else (`--gpus device=1`, `NVIDIA_VISIBLE_DEVICES=1`) and
    records the bus id of the GPU it sees before it starts; a CPU job sees no GPU. Exit codes come from
    Docker. The `srun` and `sbatch` lines of section 10 become such containers, and `scancel` in step 8
    becomes `docker stop`, which sends SIGTERM and, after 10 s, SIGKILL.
  * The Python environment `~/wf/venv` is made inside that image (Python 3.11), with `torch==2.15.0` if it can
    be installed; otherwise with the newest version that can, recorded here.
  * All code and all git go through the Mac (the PI's rule, given on 27 November after steps 2 and 3 had run):
    the cluster runs no git command and never contacts GitHub. Before the rule, step 2 had cloned the branch
    from GitHub on the cluster into `~/wf/stratego` (at `4d47425`), and the probe of step 3 had run
    `git ls-remote` and a dry-run push from there, which failed for lack of credentials and sent nothing. The
    clone stays on the cluster for now, by the PI's decision, and is not used.
  * Steps 4 to 8 use the files of this card's commit, sent from the Mac into `~/wf/runs/p0` by the commands of
    `PROGRAMME.md` section 9.2 and checked there against the commit's list of files; their output lands in that
    folder. The old tests (step 6) run before the throughput benchmark (step 5), because nothing gets GPU time
    before the tests pass (section 9.6). The probe (step 3) ran once, on the node itself: there is no separate
    login node.
  * Results come back to the Mac by one ssh call per file and are committed there and pushed to GitHub.
  * Gate of step 7, as section 10 proposes it: the closed-loop count on the 2,000 new tasks lies within 10 of
    the stored count in both formats, that is 1,507 (bf16) and 1,507 (fp32) for `v10`, and 1,309 and 1,314
    for `v11_noshared`. Step 8 passes when the first log line of the resumed job carries the round after the
    last checkpoint (41 if the stop came before round 60) and the job reaches round 119.
  * Caveat on the factor 1.84: it assumes that speed is proportional to multiply-adds. The stand-in normalises
    its state and concatenates 64 channels at every iteration; the real rule instead reads the 128-channel
    encoded input c at every iteration. If the convolutions are bound by memory traffic at these sizes, 1.84
    overstates D. Only timing the real rule (section 12.3) settles it.

* **Result:**
  * Environment (step 4): Python 3.11.10, torch 2.15.0+cu132 (CUDA 13.2 libraries; the driver reports CUDA 13.0),
    numpy 2.4.6, matplotlib 3.11.2, in the image named above. The GPU check printed `True 1 NVIDIA H100 80GB HBM3`
    from a container that saw only bus `00000000:43:00.0`. The stored numbers came from torch 2.15.0 on Python 3.13.
  * Old tests (step 6, 4 CPU cores): exit 0, six result lines, no AssertionError (`results/p0/test_sim.out`).
  * Throughput (step 5, GPU 1, 15:49:42 to 15:50:20 UTC; `results/bench/h100.json`, `h100.out`): the best
    search-mode line of "24x24 proposed rule" is **P = 300.7 million voxel-iterations per second** (bf16, standard
    layout, batch 512, 145 TFLOPS, 8.9 GiB peak). fp16 gives 298.2, fp32 with TF32 226.4. Learning mode on that
    shape: 98.6 million (fp16) and 98.4 million (bf16) at batch 16, 2.8 GiB peak. The 8x8 rule: 538.3 million
    (search), 169.3 million (learning). The wider rule: 189.5 million (search).
  * Cost model (step 9): with the registered factor, D = 1.84375 x P = **554 million**, so 6 x 10^10 / D = **108 s
    per round** and 1.5 x 10^10 / D = **27 GPU-hours per 900-round run at full scale**. The benchmark itself argues
    against the factor: the wider rule has 1.91 times the multiply-adds of the proposed one but is only 1.72 times
    slower (bf16, standard layout), and the stand-in reaches about 15% of the H100's dense bf16 peak. A straight-line
    fit of time per voxel-iteration against multiply-adds through those two shapes gives about 420 to 470 million at
    131,072 multiply-adds (fp16 and bf16), that is 32 to 36 GPU-hours per run; it scales width, not the real rule's
    input path, so it is only indicative. At D = P (no gain over the stand-in) a round takes 200 s and a run 50
    GPU-hours. Learning mode runs at a third of search speed (98.4 against 300.7 million); if the cost model's
    0.3 x 10^10 for learning leaves out the backward pass, a round costs up to about 20 s more at D = P. None of
    these figures is a bound: the real rule is not timed yet (section 12.3).
  * Re-evaluation (step 7, CPU, 16 threads each, AVX-512, bf16 autocast confirmed; `results/p0/v10_prereg.*`,
    `v11_prereg.*`, `*_versions.txt`): every count of the pre-registered evaluation (`--prereg`) equals the stored

* **Trajectories looked at:** not applicable
* **Supported, refuted or inconclusive:** not supported as registered, on the fast side: P = 300.7 million is above
  the registered 60 to 240 million (D = 1.84375 x P = 554 million, above 110 to 440). The registered refute line (P
  below 60 million) is not met, so nothing shrinks. The card registered no outcome above the range, and the excess

* **What was learned:** a full-scale run costs about 27 GPU-hours if the factor 1.84 holds, about 32 to 36 by the
  fit, and about 50 at D = P: inside or below the registered 35 to 140 and far below 140, so the dials of section 7.7
  need not shrink. bf16 (fp16 is within 1%) with the standard layout is the default for the new code; the standard
  layout beats channels-last in all four 24x24 pairs. Back-propagation through 16 iterations takes about 0.17 GiB
  per 24x24 lattice, so a learning batch of 64 legs needs about 11 GiB; in search mode a lattice takes about
  17 MiB, so a screen of 4,096 clones would need about 71 GiB of the card's 80: search memory is the binding limit,
  and the chunking of section 12.3 stays. The 8x8 evaluation is exactly reproducible on this node, so later 8x8
  numbers compare directly with the stored 75.4% and 65.5%.
