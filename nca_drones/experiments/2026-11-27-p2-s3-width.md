# Experiment card: 2026-11-27-p2-s3-width

## Before the run

* **Phase and gate it serves:** phase 2, step 3 of the chain in `PROGRAMME.md` section 12.4.
* **Hypothesis (one sentence):** widening the rule to the design's size, 32 state channels and 128 hidden units, does
  not lower closed-loop success on the 2,000 never-posed tasks, compared with step 2.
* **What would support it:** the closed-loop rate of this run (bf16, its own 2,000 never-posed tasks) is not below
  the rate of step 2 by more than max(2 s, 2 points), with s the standard deviation of the three rates of step 0
  (rule of section 12.4).
* **What would refute it:** a rate further below. Then the run is looked at on trajectories before step 4 is built
  on it.
* **The one thing that changes** relative to step 2: `--C 32 --hid 128` instead of the 16 and 64 of the measured
  rule. Weights go from 117,856 to 301,232. No code changes. Everything else is as in step 2.
* **Also reported, with no threshold:** validation success after 100, 200, 300, 450, 600 and 900 rounds beside steps
  1 and 2 (does width pay back what the codes cost in learning speed?); the seconds per round; the paired difference
  to step 2 on the 200-task test set.
* **Verification done on the cluster's CPUs first:** `test_sim.py` in the run folder, and a three-round smoke run
  with the widths.
* **How it runs:** one Docker container, CPU only, 16 cores, from `~/wf/runs/p2s3` filled from the Mac:
  `bash cluster/jobs/p2_old_recipe.sh p2s3_width_s0 0 0.5 --battery 1 --codes 1 --C 32 --hid 128 --threads 16`.
  The thread count only shortens the run, as in step 2. It starts before steps 1 and 2 have ended; if either is not
  kept, this run is void.
* **Commit:** the commit that holds this card, named in `~/wf/runs/p2s3/COMMIT`.
* **Cluster job ids:** container `wf-p2s3-s0`.   **Estimated GPU-hours:** 0 (CPU only, several hours)

## After the run

Run on 27 November 2026 from commit `8c4b695` in `~/wf/runs/p2s3` (99 of 99 files), container `wf-p2s3-s0`, CPU
only, sixteen threads. Files: `results/p2/p2s3_width_s0.*`.

* **Result:** closed loop on its 2,000 never-posed tasks: 1,674 = 83.7% (bf16; interval 82.0 to 85.3) and 1,674
  (fp32). Open loop: 1,480 = 74.0%. Test set: 182 of 200 closed, 164 open. Chosen checkpoint: round 900. Step 2:
  70.5%; step 1: 82.5%. Validation success after 100, 300, 600 and 900 rounds: 0.39, 0.66, 0.81, 0.92. About 3.8 s
  per round on sixteen threads.
* **Trajectories looked at:** none; the step is not in question.
* **Supported, refuted or inconclusive:** supported: 13.2 points above step 2.
* **What was learned:** at the design's width the recipe with codes is as good as step 1 without them (83.7% against
  82.5%, inside the spread), and it learns faster than either narrow run. Width pays back what codes cost. What this
  single run cannot say is whether a wide rule without codes would be better still; see
  `2026-11-27-p2-codes-by-width`.
* **Next step, and the card it becomes:** step 4, the task in the new simulator
* **Actual GPU-hours:** 0 (76 minutes on 16 CPU cores)
