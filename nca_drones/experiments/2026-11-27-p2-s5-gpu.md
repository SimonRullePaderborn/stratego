# Experiment card: 2026-11-27-p2-s5-gpu

## Before the run

* **Phase and gate it serves:** phase 2, step 5 of the chain in `PROGRAMME.md` section 12.4.
* **Hypothesis (one sentence):** running the rule on a GPU instead of on CPUs does not lower closed-loop success on
  the 2,000 never-posed tasks, compared with step 3.
* **What would support it:** the closed-loop rate of this run (bf16, its own 2,000 never-posed tasks) is not below
  the rate of step 3 by more than max(2 s, 2 points), with s the standard deviation of the three rates of step 0
  (rule of section 12.4). Step 4 lies between the two but changed no number: the new simulator plays the task
  exactly as the old one.
* **What would refute it:** a rate further below. bf16 arithmetic on the GPU differs from bf16 on the CPU in
  rounding only, so a real drop would point to an error in the device switch.
* **The one thing that changes** relative to step 3: `--device cuda` (with `--sim wf`, which step 4 showed to be
  exact). The rule's iterations, in search, in learning and in both evaluations, run on the GPU; observations are
  built on the CPU and moved, tubes come back to the CPU, and the simulator and the rollouts stay on the CPU. The
  final evaluation runs on the GPU too (`ANALYZE_ARGS="--device cuda"`). Model initialisation and every random
  draw stay on the CPU, so the run starts from the same weights and poses the same first tasks as step 3.
* **Also reported, with no threshold:** the seconds per round against step 3 (what the GPU buys while the rollouts
  are still on the CPU); the GPU memory used.
* **Verification done on the cluster's CPUs first:** `test_sim.py`, `python3 -m wf.test_sim`, `python3 -m
  wf.test_task8`; then a six-round smoke run on the GPU.
* **How it runs:** one Docker container that sees GPU 1 and nothing else, started only after the check on the host
  that GPU 1 is free and with the guard inside the container (as in phase 0), 16 CPU cores for the rollouts, from
  `~/wf/runs/p2s5` filled from the Mac:
  `bash cluster/jobs/p2_old_recipe.sh p2s5_gpu_s0 0 0.5 --battery 1 --codes 1 --C 32 --hid 128 --threads 8 --sim wf --device cuda`.
  It starts before steps 1 to 3 have ended; if one of them is not kept, this run is void.
* **Commit:** the commit that holds this card, named in `~/wf/runs/p2s5/COMMIT`.
* **Cluster job ids:** container `wf-p2s5-s0`.   **Estimated GPU-hours:** about 1 to 2 (one GPU held for the run, mostly idle)

## A first run that does not count, and the repeat (written before the repeat)

The first run, `p2s5_gpu_s0` from commit `e331f44`, finished on 27 November and is void for the comparison. On the
GPU a round took 0.43 s. The job script looked at the log every 30 s, so it copied `best.pt` 65 rounds after round
900, and by then the evaluation of round 950 had replaced it: the evaluated checkpoint is that of round 950 (stored
as 951), not the best one at round 900 as `EVAL_PROTOCOL.md` prescribes. Its numbers, for the record only: 1,630 of
2,000 never-posed tasks closed loop (81.5%, bf16), 170 of 200 on the test set, 900 rounds in 389 s.

The trainer now has `--stop_round`, and the job script uses `--stop_round 900` in place of watching the log. The
run is repeated unchanged otherwise, as `p2s5_gpu_s0b` from `~/wf/runs/p2s5b`, at the commit that holds this
paragraph. The hypothesis, the rule and the change under test are those written above. The CPU runs of steps 0 to 3
are not affected: at 5 to 6 s per round the old script overshoots round 900 by a handful of rounds, with no
evaluation in between.

## After the run

The repeat ran on 27 November 2026 from commit `473d7bd` in `~/wf/runs/p2s5b` (109 of 109 files), container
`wf-p2s5b-s0`, GPU 1 only. Files: `results/p2/p2s5_gpu_s0b.*`; of the void run, `p2s5_gpu_s0.json` and `.out`.

* **Result:** closed loop on its 2,000 never-posed tasks: 1,558 = 77.9% (bf16; interval 76.0 to 79.7) and 1,559
  (fp32). Open loop: 1,376 = 68.8%. Test set: 165 of 200 closed, 156 open. Chosen checkpoint: round 900. Step 3,
  the same recipe on CPUs: 83.7%. Validation success after 100, 300, 600 and 900 rounds: 0.36, 0.53, 0.73, 0.89.
  A round took 0.43 s, against 3.8 s on sixteen CPU threads; the GPU held 2.4 GB. The training of the repeat was
  identical to that of the void run, round for round; only the checkpoint differs (round 900 here, round 950
  there), and that alone moved the result from 81.5% to 77.9%.
* **Trajectories looked at:** none; the step is not in question.
* **Supported, refuted or inconclusive:** supported by the rule, narrowly: 5.8 points below step 3, where the margin
  is 5.9.
* **What was learned:** the rule runs nine times faster on the GPU while the rollouts are still on the CPU. Two runs
  of one recipe that differ only in rounding (CPU against GPU) lie 5.8 points apart, and two checkpoints of one run
  50 rounds apart lie 3.6 points apart. A single run per step therefore cannot resolve differences of a few points;
  from here on a step is run with three seeds wherever a run is cheap, starting with the card
  `2026-11-27-p2-codes-by-width`.
* **Next step, and the card it becomes:** step 6, search in closed loop
* **Actual GPU-hours:** 0.25 (two runs of about 7 minutes, and two smoke runs)
